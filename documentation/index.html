Queuezen

Social media scheduler software as a service, built with Next.js 16, React 19 and Tailwind CSS 4. Your customers connect their Facebook Pages, Instagram, Threads, X, LinkedIn, YouTube, Bluesky, Mastodon, Telegram and Discord accounts, write a post once, adapt it for every network, get it approved and let the queue publish it on time. Thank you for your purchase! This guide takes you from download to a live platform with paying customers.

Quick start: upload the queuezen folder, run npm install and npm run build, start the app and open your domain: the web installer does the rest. Then read three chapters before inviting customers: Background jobs (posts only go out on time when something calls the cron URL every minute), Media storage (Instagram, Threads and Facebook download images and videos from a public HTTPS address) and Platform setup guides (each network needs your own developer app, and some need a review).

Introduction

Queuezen lets you run your own social media management platform, in the style of Buffer, Hootsuite or Publer. Your customers sign up, create a workspace per brand or client, connect social accounts as channels and invite their team. Then they:

  • Write once, adapt per network. The composer has one shared version and a tab per channel to change the text, media, link, first comment or thread for that network only, with live previews, character counters and a check against each network's rules before anything is scheduled.
  • Schedule. Pick a date and time, add the post to the next free queue slot (weekly posting times per channel), or post it now. A calendar (month, week, list) shows everything; drag a post to move it.
  • Approve. Editors can be required to send posts for approval. Approvers, admins or clients (through a link, no account needed) approve them or send them back with a comment.
  • Automate. Bulk-import posts from a CSV file, turn RSS feed items into posts, recycle evergreen posts, and track links with UTM tags and short links.
  • Measure. Likes, comments, shares and views from the networks that offer them, top posts, results per channel and a best-time heatmap built from the workspace's own engagement.

Queuezen publishes through each network's official API with the operator's own developer apps: you, the administrator, create a Meta app, an X app, a LinkedIn app and a Google Cloud OAuth client once, and paste their keys into Admin → Platforms. Bluesky, Mastodon, Telegram and Discord need no developer app. There is no scraping, no browser automation and no password storage (Bluesky uses an app password the user can revoke). You earn money with paid plans that limit channels, scheduled posts per month, team seats, posts to X (which cost you API credits) and AI requests, and unlock RSS, the REST API and white-label approval links. Your customers pay through Stripe (automatic renewal), PayPal, Razorpay or bank transfer.

Words used in this guide: you or the administrator run the platform. Customers (users) sign up on your platform and own workspaces. Members are the people in a workspace. Clients are your customers' own clients who approve posts through a link. A channel is one connected social account (a Facebook Page, an X account, a Telegram channel…). In the examples your platform lives at https://social.example.com.
Networks change their rules. Facebook, Instagram, Threads and YouTube need an app review before your app can serve other people's accounts; until then it works for your own accounts and testers. X has no free API tier: every post costs you credits. Read Platform setup guides before you promise networks to customers.

Installation

Pick the guide that matches your hosting. Every method ends with the web installer. Right after installing, set up a 1-minute scheduler and media storage, then the networks you want to offer.

Install Queuezen on its own domain or subdomain with HTTPS, for example https://social.example.com. Every OAuth redirect URI you register at Meta, X, LinkedIn and Google is built from this address (https://social.example.com/api/oauth/<network>/callback), as are approval links, short links (/l/…), local media URLs and the cron URL. Changing the domain later means updating the redirect URIs in every developer console, and customers' old short links stop working.

cPanel / shared hosting (Setup Node.js App)

  1. In cPanel open MySQL® Databases. Create a database and a user, then add the user to the database with All privileges. Write down the database name, username and password.
  2. Create the subdomain (e.g. social.example.com) in Domains and turn on SSL/TLS Status → Run AutoSSL so it has HTTPS.
  3. Open File Manager, upload queuezen.zip (the app folder of the repository, zipped) to your home folder, e.g. /home/youruser/queuezen, and extract it. Do not put it inside public_html.
  4. Open Setup Node.js App → Create Application:
    • Node.js version: the newest available (22.x recommended)
    • Application mode: Production
    • Application root: queuezen
    • Application URL: your domain or subdomain
    • Application startup file: server.js
    Click Create.
  5. Click Run NPM Install and wait until it finishes.
  6. Copy the command shown at the top of the page (it looks like source /home/youruser/nodevenv/queuezen/22/bin/activate && cd /home/youruser/queuezen). Open Terminal in cPanel, paste it, then run: 
    npm run build
    The build takes 1–4 minutes.
  7. Back in Setup Node.js App, click Restart. Open your domain: you will see the installer.
  8. After installing, add the cron job from Admin → System (see Cron URL). On cPanel this is required for punctual posts: Passenger stops idle apps, and lazy mode only runs while people use the site.

server.js starts the built Next.js app, which serves everything: pages, approval links, short links, the API, local media files and the files in public. You don't need to copy anything into public_html.

If the build stops with “JavaScript heap out of memory” your plan limits memory. Build on your own computer instead (npm install && npm run build), then upload the whole folder including the .next folder, and only run “Run NPM Install” + “Restart” on the server.
Shared hosting often limits the size of uploads (Apache LimitRequestBody, a proxy in front of Passenger) and request time. Images work everywhere; for videos of hundreds of MB use an S3-compatible bucket (browsers then upload straight to the bucket) or a VPS.

VPS (Ubuntu) with PM2 and Nginx

  1. Install Node.js 22, Nginx and PM2: 
    curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs nginx
sudo npm install -g pm2
  2. Install MySQL (or use SQLite and skip this step): 
    sudo apt install -y mysql-server
sudo mysql -e "CREATE DATABASE queuezen CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'queuezen'@'localhost' IDENTIFIED BY 'choose-a-strong-password';
GRANT ALL PRIVILEGES ON queuezen.* TO 'queuezen'@'localhost'; FLUSH PRIVILEGES;"
  3. Upload the queuezen folder to /var/www/queuezen, then build: 
    cd /var/www/queuezen
npm ci
npm run build
  4. Choose a cron secret and start the app and the worker with PM2. ecosystem.config.cjs starts two processes: queuezen (the web app) and queuezen-worker (runs the background jobs every 15 seconds). Both get the same CRON_SECRET: 
    export CRON_SECRET="$(openssl rand -hex 24)"
echo "$CRON_SECRET"          # keep a copy
pm2 start ecosystem.config.cjs
pm2 save && pm2 startup

    Always set your own CRON_SECRET before pm2 start. Without it the worker can't run jobs (PM2 prints a warning and the worker exits), and a CRON_SECRET line in .env.local is only seen by the worker, not by the app. Export the variable before pm2 start (as above) or write your secret into ecosystem.config.cjs. Use at least 12 random characters: the app ignores shorter values and the example value change-me-to-a-long-random-string. After changing it run pm2 restart ecosystem.config.cjs --update-env.

  5. Create /etc/nginx/sites-available/queuezen: 
    server {
    listen 80;
    server_name social.example.com;
    # Largest upload: keep it above "Largest video (MB)" in Admin → Settings → Media storage.
    client_max_body_size 600m;

    # Media uploads to local storage are streamed to disk: don't buffer them.
    location /api/media/upload {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_request_buffering off;
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_read_timeout 90s;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
    client_max_body_size matters: Nginx's default is only 1 MB, so without it every image upload above 1 MB fails with 413. X-Forwarded-For is used for rate limits, X-Forwarded-Proto for secure cookies. proxy_read_timeout 90s leaves room for “Post now” and the cron URL. Enable the site and add a free SSL certificate: 
    sudo ln -s /etc/nginx/sites-available/queuezen /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d social.example.com
  6. Open https://social.example.com to run the installer. Afterwards, Admin → System → Scheduler should show Running with the source worker within a minute.
Keep instances: 1 for the web app in ecosystem.config.cjs: rate limits are kept per process. If you ever run several app servers, set the same APP_SECRET and NEXT_SERVER_ACTIONS_ENCRYPTION_KEY on all of them and use S3-compatible storage (or a shared storage folder). The worker calls http://localhost:3000 by default; set WORKER_URL if the app listens elsewhere.

Docker

The app folder includes a Dockerfile and a docker-compose.yml with three services: app (the web app), worker (runs background jobs every 15 seconds) and db (MySQL 8.4). First create a file named .env next to docker-compose.yml with your own secret:

CRON_SECRET=paste-a-long-random-string-here

Then start everything:

cd queuezen
docker compose up -d --build

Open http://your-server:3000. In the installer choose MySQL with host db, port 3306, database queuezen, user queuezen, password queuezen (change these and MYSQL_ROOT_PASSWORD in docker-compose.yml first). The storage folder (configuration, the generated app secret, uploads and media on local storage) is kept in a Docker volume. Put Nginx, Caddy or Traefik with HTTPS in front of port 3000 (with a large enough upload size, see the Nginx example above), and make sure it sends X-Forwarded-For and X-Forwarded-Proto.

docker-compose.yml refuses to start until CRON_SECRET is set in the .env file next to it (at least 12 random characters). The included .dockerignore keeps local node_modules, .next and storage folders out of the image.

Without Compose:

docker build -t queuezen .
docker network create queuezen-net
docker run -d --name queuezen --network queuezen-net -p 3000:3000 \
  -e CRON_SECRET=your-secret -v queuezen-storage:/app/storage queuezen
docker run -d --name queuezen-worker --network queuezen-net \
  -e WORKER_URL=http://queuezen:3000 -e CRON_SECRET=your-secret queuezen node scripts/worker.mjs

Vercel (with TiDB Cloud and Cloudflare R2 or Vercel Blob)

Vercel has no permanent disk, so the web installer, SQLite and local media storage can't be used there. Queuezen is configured with environment variables, a cloud MySQL-compatible database such as TiDB Cloud Serverless (free tier), Aiven or PlanetScale, and an object store for media: Cloudflare R2 (or any S3-compatible bucket) or Vercel Blob. Browsers upload media straight to the bucket, so Vercel's 4.5 MB request body limit doesn't apply to videos.

  1. Create a database. In TiDB Cloud: create a Serverless cluster in the region closest to your Vercel functions, open Connect, generate a password and note the host, port (4000), user and password. In the SQL editor run CREATE DATABASE queuezen;
  2. Create the media storage: an R2 bucket with a public custom domain and a CORS rule (see S3 / R2), or a Vercel Blob store (Vercel → Storage → Create → Blob, then connect it to the project; Vercel adds BLOB_READ_WRITE_TOKEN automatically).
  3. Fork this repository on GitHub (or push your copy to your own repository).
  4. In Vercel click Add New → Project, import the repository and set Root Directory to the folder that contains package.json. Keep the default build command (npm run build).
  5. Add these Environment Variables: 
    DB_DRIVER=mysql
DB_HOST=gateway01.ap-southeast-1.prod.aws.tidbcloud.com
DB_PORT=4000
DB_USER=xxxxxxxx.root
DB_PASSWORD=your-password
DB_NAME=queuezen
DB_SSL=true
APP_INSTALLED=true
ADMIN_EMAIL=you@example.com
ADMIN_PASSWORD=a-strong-password
ADMIN_NAME=Your Name
SITE_URL=https://social.example.com
CRON_SECRET=a-long-random-string
APP_SECRET=another-long-random-string

# Media on Cloudflare R2 …
STORAGE_DRIVER=s3
S3_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com
S3_REGION=auto
S3_BUCKET=queuezen-media
S3_ACCESS_KEY_ID=…
S3_SECRET_ACCESS_KEY=…
S3_PUBLIC_URL=https://media.example.com
# … or on Vercel Blob (BLOB_READ_WRITE_TOKEN is added when you connect the store)
# STORAGE_DRIVER=blob
    Instead of the DB_* variables you can set one DATABASE_URL=mysql://user:password@host:4000/queuezen?ssl=true.
  6. Click Deploy. Tables are created automatically on the first visit and the administrator account is created from ADMIN_EMAIL / ADMIN_PASSWORD.
  7. Add your domain in Settings → Domains, and set the same address in Admin → Settings → General → Site URL.
  8. In Vercel open Settings → Functions and choose the region closest to your database.
  9. Set up the scheduler as described in Vercel & serverless. This step is not optional: Vercel Hobby cron runs only once a day.

Vercel is fine for a demo or a small platform. Keep in mind:

  • Set APP_SECRET (16+ random characters). It encrypts the access tokens of every connected channel. See Privacy & compliance.
  • There is no worker process: publishing depends on an external cron service calling the cron URL every minute (or Vercel Pro cron).
  • Choose S3/R2 or Blob in Admin → Settings → Media storage (or with STORAGE_DRIVER): the media library refuses uploads to local storage on Vercel.
  • Uploading a long YouTube video can take several ticks; it resumes where it stopped. For many large videos a VPS is the better host.
  • Vercel Hobby is for non-commercial use. Use Vercel Pro (or a VPS) for a paid platform.

Background jobs & scheduling

Pages, the API and approval links answer immediately; that never depends on the scheduler. But publishing a scheduled post is a background job, and something must start it. Read this chapter before you invite customers.

Why publishing needs a cron job every minute

A post scheduled for 09:00 is published by the first scheduler tick that runs at or after 09:00. Queuezen can't wake itself up at 09:00: a web app only runs when a request arrives. So:

  • A tick every minute (cron URL) publishes posts within about a minute of their time. The worker ticks every 15 seconds.
  • Lazy mode (the default) runs a tick only after someone opens a page: at night, posts wait until the next visitor.
  • Vercel Hobby cron jobs run once a day: a post scheduled for 09:00 could go out the next morning.
Without a 1-minute cron job or the worker, scheduled posts are late, tokens of X and YouTube channels aren't refreshed in time, RSS feeds aren't read and analytics aren't collected. “Post now” in the composer still works (it publishes inside the request).

The jobs

A tick runs these jobs one after the other within a time budget (cron URL and worker 45 seconds, lazy mode 8 seconds, Run jobs now 25 seconds). A lock in the database makes sure two ticks never run at the same time; whatever doesn't fit is picked up by the next tick. The publish, rss, recycle and metrics jobs skip the workspaces of owners an administrator has banned.

The cron secret

  • If the environment variable CRON_SECRET is set (at least 12 characters, not the example value), that value is the secret.
  • Otherwise Queuezen creates a random secret the first time it is needed and stores it in the database.

Open Admin → System: the Scheduler card shows the complete Cron URL (with a Copy button) and a ready-made cron line. New secret replaces a stored secret, e.g. if it leaked; the old URL stops working immediately. While the secret comes from CRON_SECRET, change the environment variable instead and restart.

curl -fsS "https://social.example.com/api/cron/tick?key=YOUR-SECRET"
curl -fsS -H "Authorization: Bearer YOUR-SECRET" https://social.example.com/api/cron/tick

GET and POST both work. A correct call answers with a JSON summary, for example {"source":"cron","startedAt":"…","jobs":{"publish":3,"token-refresh":0,"rss":1,"recycle":0,"metrics":12,"housekeeping":0},"failed":[],"skipped":[],"durationMs":4210,"skippedLocked":false}. The numbers are the items each job handled (publications claimed, tokens refreshed, posts created from feeds, recycled posts, posts measured, rows cleaned up). A wrong or missing secret answers 401; more than 30 calls per minute from one IP address answer 429; "skippedLocked":true means another tick was still running.

Lazy mode and choosing a method

With Admin → Settings → Scheduler → Run background jobs on visits switched on (default), the platform runs a tick after it has answered a page request, whenever no tick ran during the last minute (8-second budget; each server process tries at most every 15 seconds). Media storage

Images and videos of the media library live in one of three storages, chosen in Admin → Settings → Media storage. Uploads never pass through a serverless function: the browser sends the file straight to the storage (a presigned S3 PUT, a Vercel Blob client token), or, on local storage, streams it to the server's disk.

Why media must be publicly reachable

Networks receive media in two ways:

The network downloads a public URLQueuezen uploads the bytes
Instagram (both logins), Threads, Facebook (photos, videos, Reels), Telegram (files up to 5 MB images / 20 MB videos; larger ones are uploaded)X, LinkedIn, YouTube, Bluesky, Mastodon, Discord (Queuezen reads the file from your storage and sends it in parts)

For the first group, Meta's servers fetch the file from its URL in your library, so that URL must be public HTTPS, without redirects and without login, and stay reachable while Instagram processes it (Instagram containers live 24 hours). That is why a localhost installation, a private bucket or a site behind HTTP basic auth can't post images to Instagram. Media files are never deleted while a scheduled or pending post uses them.

Local disk (VPS, cPanel, Docker)

  • Files go to storage/uploads/media/w<workspace>/<year>/<month>/<random>-<name>.<ext> and are served at https://social.example.com/api/media/f/… with byte ranges, long caching and safe headers. The random part makes addresses impossible to guess.
  • Uploads are streamed to disk by PUT /api/media/upload with a signed, 2-hour upload token: large videos never sit in memory. Your proxy must allow large bodies (client_max_body_size in Nginx, see the VPS guide).
  • Needs a permanent disk: not for Vercel or other serverless hosts. Back up storage/uploads with your database.

Meta app (Facebook, Instagram, Threads)

One Meta app serves Facebook Pages and both Instagram logins; Threads is a use case of the same (or a separate) app with its own app ID. Prepare these first, Meta asks for them:

  • A Facebook account with access to Meta Business Suite and a business portfolio for your company (needed for Business Verification).
  • Your privacy policy URL https://social.example.com/p/privacy-policy and terms URL https://social.example.com/p/terms-of-service (default pages created by the installer; review them first, see Compliance).
  • The data deletion request URL https://social.example.com/api/meta/data-deletion and the deauthorize (uninstall) callback URL https://social.example.com/api/meta/deauthorize. Admin → Platforms → Meta callbacks shows all four URLs with Copy buttons.
  • An app icon (1024 × 1024 px) and a contact email.

The two Meta callbacks do different things. Meta calls the deauthorize URL (POST /api/meta/deauthorize) when a person removes your app from their Facebook, Instagram or Threads account: Queuezen verifies the signed_request with your Meta, Instagram or Threads app secret and disconnects that person's channels (their tokens stop working anyway; scheduled publications are cancelled and their monthly quota is given back). It calls the data deletion URL when the person asks for their data to be deleted: Queuezen also removes the channels' profile data and answers with a confirmation code (see Compliance). Enter each URL in the matching field; the guides below say where.

Permissions requested: pages_show_list, pages_manage_posts, pages_read_engagement, pages_manage_engagement (first comments), publish_video, read_insights. Graph API version v26.0.

  3. In Facebook Login for Business → Settings, add https://social.example.com/api/oauth/facebook/callback (and …/api/oauth/instagram/callback) to Valid OAuth Redirect URIs. On the same page, enter https://social.example.com/api/meta/deauthorize as Deauthorize callback URL.

Every thread part and every first comment is a separate post. Check docs.x.com/x-api/getting-started/pricing for current prices.

  • Limit what customers can spend: Admin → Plans → Posts to X per month (0 = X not allowed on that plan, -1 = unlimited). The defaults are 0 (Free), 100 (Pro) and 500 (Agency).
  • Enter your monthly budget in Monthly X API budget (USD) (x_monthly_budget): Admin → Platforms then shows a spend meter (this month's estimated cost against the budget, red when exceeded). It is a meter only: the real limit is the spend limit you set at console.x.com.

Testing vs. verification

  • While the consent screen is in Testing, only up to 100 test users you list can connect, and Google lets their refresh tokens expire after 7 days: the channel then shows expired and must be reconnected. Fine for trying, not for customers.
  • youtube.upload is a sensitive scope. In production, unverified apps show “Google hasn't verified this app” and are limited in users. Submit the app for OAuth verification (Verification Center). Google usually asks for: a verified domain with your home page, a privacy policy on that domain that explains what you do with Google user data and follows the Google API Services User Data Policy (including Limited Use), and an unlisted YouTube demo video showing the consent screen (with your app name and the OAuth client ID visible in the address bar), connecting a channel, uploading a video from the composer and the video on YouTube.
  • Google may keep videos uploaded by projects that haven't passed the YouTube API Services audit as private; complete the audit (and the quota extension form) before you sell YouTube publishing. The YouTube API Services Terms also require your terms and privacy pages to link to the YouTube Terms of Service and the Google Privacy Policy, and to explain how users revoke access (myaccount.google.com/permissions).

Since 1 June 2026 a Cloud project may upload 100 videos per day (its own bucket), and other calls share the default 10,000 quota units per day (a custom thumbnail costs 50 units, reading statistics 1 unit per request). User guide

This chapter describes the customer dashboard (/dashboard). You can share it with your customers or copy parts into your own help pages. Each workspace has its own menu: Overview, Compose, Calendar, Queue, Posts, Media, Analytics, Automation (RSS, recycling), Links, Channels, Team (members, approvals), Notifications, API keys and Settings. Every account gets a personal workspace; agencies create one workspace per client with New workspace (switcher at the top of the menu; up to 50 owned workspaces per account). Connecting channels

Channels → Connect shows the networks the administrator has set up. OAuth networks open the network's consent screen and return to Queuezen; when the network shares several accounts (Facebook Pages, Instagram accounts), you pick which ones to add. Bluesky, Telegram and Discord show a short form; Mastodon asks for the server first. See Platform setup guides for what each network needs from the user (Instagram Business/Creator account, Telegram bot as admin, Bluesky app password…).

  • Each channel card shows its status: active, expired (the token expired or was revoked: click Reconnect; scheduled posts wait and continue afterwards), error (the last test or post failed for another reason) or disconnected. LinkedIn channels show when their 60-day access ends, and Expires soon from 7 days before (the Overview page lists them too).

The composer

  1. Channels. Tick the channels to post to (Select all / Clear). A warning appears when a selected channel needs to be reconnected.
  2. Shared version. Write the text (with emoji picker and hashtag groups), add images and videos from the media library (reorder them, they keep their alt text), a link (attached as a link card where the network supports it), a first comment and thread parts. Add labels to find posts later.
  3. Per-channel tabs. Each selected channel has a tab. Changing a field there overrides it for that channel only (the tab shows Customised; Use the shared version resets it).   4. Preview and checks. The preview shows the post as each network displays it. Counters count like the network (X weights URLs as 23 and emoji/CJK as 2, Bluesky counts graphemes, Mastodon counts URLs as 23). Problems (wrong image type for Instagram, a video too long for X, a missing YouTube title…) block scheduling until fixed; Worth a look warnings don't.
  5. Save. Save draft, Send for approval, Schedule, Add to queue or Post now (see below). Drafts are autosaved while you type.

The first comment is posted right after the post: as a comment on Facebook, Instagram and LinkedIn, as a self-reply on X, Threads, Bluesky and Mastodon (YouTube, Telegram and Discord don't support it). Thread parts are posted as replies in order on X (25 parts), Threads (20), Bluesky and Mastodon; other networks get the first part only. Use the first comment for hashtags on Instagram, or for the link on networks that reach fewer people when a post contains a link. On X every reply is a billed post.

AI assistant

When the administrator has set up an AI provider and the plan includes it, the AI button offers: rewrite for the selected network (with a tone: friendly, professional, witty, bold, casual, inspiring), shorten to fit, hashtags, translate (25 languages), generate a post from a topic or a link (the page's title and description are read), and three first comment ideas. How publishing works (and why posts aren't duplicated)

  1. When a post is due, the engine claims each of its channel publications with a database update that only one process can win, and holds a 3-minute lease (renewed during long uploads). Two ticks, a cron call and “Post now” can never publish the same publication twice.
  2. Before every irreversible step (upload done, Instagram container created, X media id, YouTube upload session, post sent) the driver saves its progress. A run that times out or crashes resumes from there instead of uploading again.
  3. Before any retry, Queuezen first looks on the network for the post the earlier attempt may have created (X, LinkedIn and Facebook have no idempotency key; Mastodon has one); if it exists, the publication is marked published without posting again.
  4. If that lookup itself fails on any network (the network doesn't answer), Queuezen doesn't post blindly: it waits 2 minutes and checks again (“Couldn't check whether an earlier attempt already published this post. Checking again shortly.”). After 3 failed checks (two waits) it publishes anyway rather than losing the post, and the publication is flagged as a possible duplicate on the post page (“… it may appear twice on the network”): look at the account and delete the extra copy if there is one.

Short links and UTM tags

Links lists the workspace's tracked short links: https://social.example.com/l/<code> redirects (302) to the destination with its UTM parameters (utm_source, utm_medium, utm_campaign, utm_term, utm_content) and counts clicks per day. Create links here, from the composer's Shorten button, or let RSS feeds create them. KPIs show the number of links and clicks in the last 30 days and in total, with a daily chart. Bots, link-preview fetchers and prefetches are not counted, and no personal data is stored (no IP address, cookie or user agent). Deleting a link stops its redirect at once. Up to 5,000 links per workspace.

Links in published posts

With Settings → Links in posts, the publishing engine adjusts the links of every post when it publishes it, separately for each channel. The post as written (composer, calendar, CSV, API) stays unchanged.

  1. UTM tags. The channel's choice decides: Workspace default uses the workspace's values when Add UTM tags to links is on; Custom for this channel always adds the channel's own values; None for this channel adds nothing. Tags go on every http(s) link in the text, the first comment and the thread parts, and on the link field. {platform} becomes the network (facebook, x, linkedin…). Parameters a link already has (for example from the composer's UTM builder) are kept, not overwritten.
  2. Short links. With Shorten links on, every link (already tagged) is replaced with a tracked short link https://social.example.com/l/<code>, recorded with the post and channel so the Links and Analytics pages count its clicks. A retry reuses the short link already made for that post, channel and destination. If a short link can't be created (for example at the 5,000-link limit), the original link is posted.
  3. Your own short links are left alone. Links that already point to your /l/… addresses (made with the composer's Shorten button, on the Links page or by an RSS feed) get no UTM tags and aren't shortened again: they keep the UTM values stored with them.

When UTM tags or short links are on for a channel, the composer also counts the links in their final form (the short link's length, or the link with its UTM tags) and warns when that would go over the network's limit, which matters on networks that count links in full (Bluesky, Threads, Telegram captions). If it happens when publishing, that text (or thread part, or first comment) is posted with the original links instead of failing, and the publishing history says so.

How Queuezen protects connected accounts

  • Tokens are encrypted at rest. Access and refresh tokens, Bluesky app passwords and sessions, Telegram bot tokens, Discord webhook URLs and Mastodon app secrets are stored with AES-256-GCM, with a key derived (HKDF-SHA256) from the app secret for each purpose. They are decrypted only inside the publishing engine and the drivers and are never sent to the browser, the REST API or notifications.
  • OAuth flows use a signed state bound to the user and workspace, PKCE where the network supports it, and a short-lived encrypted cookie (qz_oauth, 15 minutes). Connections started in one browser can't be finished in another.
  • API keys are stored as SHA-256 hashes, approval-link tokens as hashes, passwords with scrypt. Outgoing requests to user-entered addresses (Mastodon servers, RSS feeds, link cards, webhooks, media imports) refuse private and local networks.
  • Disconnect deletes a channel's tokens, cancels its scheduled publications and, where the network has an API for it, revokes access (X, LinkedIn, YouTube, Mastodon, Bluesky session). For Facebook, Instagram and Threads the person can also remove the app in their Meta settings; Discord webhooks and Telegram bots are removed in those apps.

The app secret (APP_SECRET)

Queuezen takes the secret from, in order: the environment variable APP_SECRET (at least 16 characters); appSecret in storage/config.json (generated on first use); an app_secret row in the database when that file can't be written.

Set APP_SECRET yourself (e.g. openssl rand -hex 32) on Vercel and other serverless hosts, and whenever several servers or containers run the app. Never change or lose it once customers have connected channels: tokens encrypted with another secret can't be read, the channels show expired (“The channel has no access token: reconnect it.”) and every customer must reconnect every channel. Back up storage/config.json (or your APP_SECRET) together with the database.

Data deletion

  • Meta deauthorize (uninstall) callback https://social.example.com/api/meta/deauthorize: when a person removes your app from their Facebook, Instagram or Threads settings, Meta POSTs a signed_request. Queuezen verifies it with your Meta, Instagram or Threads app secret (an invalid signature gets 400) and disconnects that person's channels: tokens deleted, scheduled publications cancelled. Their profile data stays until a data deletion request.
  • Meta data deletion callback https://social.example.com/api/meta/data-deletion: when a person asks for their data to be deleted, Meta sends a signed request the same way. Queuezen disconnects that person's channels, deletes their tokens and profile data (the channel is renamed “Deleted account”), and answers with a confirmation code and a status page (…/api/meta/data-deletion?code=…) as Meta requires.
  • Customers delete posts, media, channels and workspaces themselves; deleting a workspace (owner only, Settings → Delete workspace) removes its media files from storage. You delete accounts in Admin → Users (payments are kept for accounting). Handle other deletion requests the same way and confirm them within the time your law requires.
  • Analytics are only fetched for posts published through Queuezen. Short links store daily click counters only (no IP, cookie or user agent).

Performance & data retention

  • Throughput. Each tick publishes until 70% of its budget is used, at most 3 publications per channel per tick (bursts are spread so networks don't see a flood), 4 channels in parallel. An image post usually takes 1–3 seconds per channel, so a worker (4 ticks a minute) or a 1-minute cron handles hundreds of publications an hour; videos take longer and resume across ticks.
  • One process: keep one app process (instances: 1); rate limits are per process. The worker and cron can run alongside safely.
  • Database: SQLite is fine for testing and small platforms; use MySQL/MariaDB for production. The included indexes cover the engine's queries (due publications, leases, calendars, analytics).
  • Media: prefer an S3-compatible bucket with a CDN/custom domain for many large videos; uploads go straight from the browser to the bucket.
  • Rate limits use the connecting IP address from X-Forwarded-For. Set TRUSTED_PROXY_HOPS correctly when Cloudflare is in front of Nginx.

Adding a platform driver

A driver is a stateless object implementing SocialDriver (src/social/types.ts):

interface SocialDriver {
  readonly platform: Platform;
  connectStart(ctx, input): Promise<{ kind: "redirect"; url; carry? } | { kind: "form"; fields }>;
  connectFinish(ctx, input): Promise<ConnectedAccount[]>;          // one or more accounts to add
  refresh(ctx, channel): Promise<RefreshResult | null>;             // new credentials before expiry
  testConnection(ctx, channel): Promise<TestResult>;
  publish(ctx, input: PublishInput): Promise<PublishResult>;        // { externalId, permalink, threadIds?, firstCommentId?, warnings? }
  deleteRemote(ctx, channel, externalId): Promise<void>;
  fetchMetrics(ctx, channel, items): Promise<MetricsResult[]>;      // [] when the network has no analytics
  findExisting(ctx, input): Promise<{ externalId; permalink } | null>;  // idempotency check before retries
}
// Throw only DriverError(message, kind, { status, code, retryAfterMs, retryable }) with kind
// "auth" | "rate_limit" | "validation" | "media" | "network" | "quota" | "unknown".
  1. Add the id to PLATFORMS (and V1_PLATFORMS to list it on the connect screen) in src/social/types.ts, and its entry in PLATFORM_CAPABILITIES (src/social/platforms.ts): limits, media rules, auth kind and scopes. Validation, counters and the per-account limits then work automatically.
  2. Add its name, colour and icon to PLATFORM_STYLES in src/social/format.ts.
  3. Create src/lib/platforms/<id>.ts. Use ctx.fetch (never the global fetch: it applies the private-address guard and lets tests record answers), ctx.redirectUri for OAuth and ctx.app for your credentials. Call input.saveState({...}) before every irreversible step (upload finished, post created) and read input.target.uploadState to resume; return a usage block ({ posts, uploads, apiCalls, costMicros }) for the meters. Copy mastodon.ts or telegram.ts as a starting point.
  4. Register the driver in BUILTIN_DRIVERS (src/lib/platforms/drivers.ts). The Simulated driver covers every id in PLATFORMS automatically.
  5. If it needs your developer app: add setting keys to SETTING_DEFAULTS (and secrets to SECRET_SETTINGS) in src/lib/settings.ts, a case in appConfigFor() (runtime.ts), a SetupGuide in setup-guide.ts (the wizard renders it) and, optionally, a credential test in app-test.ts.
  6. Network options: extend PlatformOptions and normalizePlatformOptions(), and the composer's options panel. Texts go to src/lib/i18n/messages.ts.

After editing code always run npm run typecheck, npm run build and restart the app and the worker.

Updating to a new version

  1. Back up the storage folder (it holds config.json with the app secret, and media on local storage) and your database.
  2. Replace all files except storage (and your .env file and edited ecosystem.config.cjs, if any) with the new version.
  3. Run npm install and npm run build.
  4. Restart the app and the worker: pm2 restart all, docker compose up -d --build, or Restart in cPanel.

Database changes are applied automatically the first time the new version starts. Channels (and their tokens), posts, queue slots, media, short links and API keys are kept. Publications that were in flight resume after the restart (their lease expires and the next tick continues them; the lookup before retry prevents duplicates). After an update, re-check Admin → Platforms: new versions may request a new permission, in which case customers reconnect that network.

Duplicate post concerns

Queuezen is built to never publish a publication twice: each one is claimed by exactly one process with a lease, progress is saved before every irreversible step, and before any retry it first looks on the network for the post an earlier attempt may have created (Mastodon also gets an idempotency key). Running the worker, a cron job and lazy mode together is safe. If you still see a duplicate:

  • Check that you don't run two installations (e.g. a staging copy) on the same database, or two databases with the same channels connected: each would publish the same post.
  • Check for two posts with the same content (e.g. a CSV imported twice, an RSS feed added twice, a recycled copy): duplicates created by the user are separate posts.
  • When a network can't be asked whether the post exists (the lookup itself fails), X, LinkedIn and Facebook publications wait 2 minutes and check again; only after 3 failed checks does Queuezen publish anyway, and the publication is then flagged as a possible duplicate on the post page. Look for that note, check the account and delete the extra copy on the network if there is one.

Support

If something isn't working, please read Troubleshooting first, and check Admin → System → Scheduler and Admin → Platforms (Test button). For further help, open an issue on GitHub. Please include your hosting type, Node.js version, database (MySQL or SQLite), how you run background jobs (cron, worker, lazy), your media storage, the network concerned, the exact error from the post page's publishing history or the network's consent screen, and any error from the browser console or the server log. Bug reports and pull requests are welcome. For a hosted version, paid installation or customisation, contact EpiFive.
